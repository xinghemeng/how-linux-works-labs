# simple-sched-lab 实验设计

本文是基础实验的内容说明与任务清单。代码风格见 `code_review_c.md`、`code_review_cpp.md`。

C 是基准实现；C++17 与之对外行为一致，用来对照学习系统编程。实现不必复刻书中示例源码，但实验目标和要采集、要观察的内容与书中这一节相同。

## 用语

本实验只区分两种时间，全文都用这两套说法，不要混用。

| 说法 | 含义 |
| --- | --- |
| **CPU 时间** | 进程实际占用处理器执行了多久。被调度出去的那段时间不计入。 |
| **经过的时间** | 从某个起点到现在，现实中过了多久。用单调时钟 `CLOCK_MONOTONIC` 测量（不受系统调时影响）。进程在等待 CPU 时，这项仍在增加。输出字段名是 `elapsed_ms`。 |

`total`、`resol` 描述的是要完成的 **CPU 工作量**；`elapsed_ms` 是 **经过的时间**。多个进程争用同一颗逻辑 CPU 时，工作量不变，经过的时间会被拉长。

其它固定说法：

| 说法 | 含义 |
| --- | --- |
| **忙等** | 不调用 `sleep`，持续占用 CPU 空转。 |
| **逻辑 CPU** | 操作系统眼里的一颗可调度处理器（超线程也算一颗）。 |
| **参数 `nproc`** | 同时运行的进程个数。与同名命令 `nproc(1)`（查看逻辑 CPU 个数）不是一回事。 |
| **僵尸进程** | 子进程已退出，但父进程尚未 `wait`，进程表项还在。 |

## 1. 实验目标

同时运行一个或多个只做忙等的进程，采集：

1. 某一时刻，逻辑 CPU 上运行的是哪一个进程
2. 每个进程的运行进度

据此核对教材对调度器的描述：可运行进程被分时放到逻辑 CPU 上，可以被抢占；进度随 CPU 时间增加，等待 CPU 时进度不增加。

程序只负责输出数据。不要在代码里断言调度必须均匀轮转。结论写在观测记录里。

## 2. 实验内容

### 2.1 命令行

```text
./sched_c   nproc total resol
./sched_cpp nproc total resol
```

| 参数 | 含义 |
| --- | --- |
| `nproc` | 同时运行的进程个数，整数，`≥ 1` |
| `total` | 每个进程要完成的工作量，单位毫秒。含义是「独占 CPU 时大约要跑这么久」，不是 `sleep(total)` |
| `resol` | 采样间隔，单位毫秒。每做完约 `resol` 毫秒的工作记一条。`total` 必须能被 `resol` 整除 |

`nrecord = total / resol`，每个进程恰好 `nrecord` 条记录。参数不合法则向标准错误输出说明原因，并以非零状态退出。

### 2.2 运行过程

1. 启动前准备好「一份大约对应 `resol` 毫秒 CPU 时间的忙等」。书中用空循环标定每毫秒循环次数，再乘以 `resol`。标定或计量必须在 `fork` 之前完成，否则会和子进程争用 CPU，标定失准。
2. 用 `CLOCK_MONOTONIC` 记下程序开始时刻。
3. `fork` 出 `nproc` 个子进程，实验编号为 `0 … nproc-1`。不要用线程代替进程。
4. 每个子进程重复 `nrecord` 次：做完一份忙等，再读一次单调时钟。忙等过程中禁止 `sleep` / `nanosleep`。
5. 进度为 `(i + 1) * 100 / nrecord`（`i` 从 0 计），最后一次为 100%。
6. 该进程的工作全部完成后，按 2.3 的格式输出自己的记录。父进程等待全部子进程结束后再退出。`fork` 失败时，结束已创建的子进程并 `wait`，不要留下僵尸进程。

### 2.3 输出

制表符分隔，一行一条：

```text
<id>\t<elapsed_ms>\t<progress>
```

| 列 | 含义 |
| --- | --- |
| `id` | `0 … nproc-1` |
| `elapsed_ms` | 从程序开始到该采样点的经过的时间，毫秒 |
| `progress` | 该进程进度，百分数 |

分析时横轴用 `elapsed_ms`：某条记录出现，说明该 `id` 当时刚做完一份忙等，它正在或刚刚占用逻辑 CPU。多个进程共享一颗逻辑 CPU 时，各 `id` 的时间戳会交错，从开始到全部结束的经过的时间大约按进程数拉长；独占一颗逻辑 CPU、或逻辑 CPU 足够时，经过的时间接近 `total`。

### 2.4 实现不必与书中示例相同

书中要点：**用固定工作量的忙等表示「resol 毫秒的工作」，用经过的时间做横轴**。下面可以替换，只要 2.1–2.3 的含义不变。

| 书中做法 | 本仓库可以 |
| --- | --- |
| 空循环标定 `loops_per_msec()` | 用进程 CPU 时钟等到 `resol` 毫秒；若仍用标定，循环不能被编译器删掉 |
| 子进程把时间戳写入缓冲区，结束时自己 `printf` | 也可以由父进程汇总后再打印。忙等过程中不要打印，以免干扰计时 |
| `atoi` / `err` / `warn` | 按本仓库 C / C++ 规范解析参数、处理错误 |
| `fork` 失败时 `kill(SIGINT)` | 能结束子进程并 `waitpid` 即可 |

空语句循环 `for (i = 0; i < n; i++) ;` 在开启优化时可能被删掉。无论是否标定，忙等必须真正占用 CPU。

### 2.5 推荐观测

先查看本机逻辑 CPU 个数（命令 `nproc(1)` 或读 `/proc/cpuinfo`）。初次试跑可用较小的 `total`；要看清时间片，再把 `total` 加大（书中常用秒级，`resol` 为几十到一百毫秒）。

| 编号 | 做法 | 预期（以实测为准） |
| --- | --- | --- |
| A | `nproc=1` | 经过的时间约等于 `total`；只有一个 `id`；进度匀速到 100% |
| B | `nproc=2`，绑定到 1 颗逻辑 CPU（如 `taskset -c 0`） | 两个 `id` 的采样在横轴上交错；进度交替上升；经过的时间大约是 A 的两倍 |
| C | `nproc=2`，不绑定，且机器不少于 2 颗逻辑 CPU | 两条进度线更可能同时推进，经过的时间接近 A，交错减弱 |

把标准输出存成 tsv，画两张图：

1. 横轴 `elapsed_ms`，纵轴 `id`：哪个进程在什么时候留下了采样。
2. 横轴 `elapsed_ms`，纵轴 `progress`，按 `id` 分线：进度如何随经过的时间增长。

### 2.6 工程约定

- 代码只放在 `sched_c/` 或 `sched_cpp/` 内，不要跨目录互相 `#include`。
- 配置与编译：`cmake --preset sched-c` / `sched-cpp`，再 `cmake --build --preset sched-c` / `sched-cpp`。clangd 分别使用 `out/build/sched-c` 与 `out/build/sched-cpp` 中的 `compile_commands.json`。
- 编译选项：`-Wall -Wextra`。不要使用 `-Werror`。

## 3. 任务清单

本阶段只做基础实验（与书中这一节同等的内容）。

### 3.1 C 基准（`sched_c`）

- [ ] 校验 `nproc` / `total` / `resol`（含 `total` 能被 `resol` 整除），失败则说明原因并以非零状态退出
- [ ] `fork` 前准备好每份 `resol` 毫秒忙等；记下启动时刻
- [ ] `fork` 出 `nproc` 个子进程；失败则结束已创建的子进程并 `wait`
- [ ] 子进程做 `nrecord` 次忙等并记录经过的时间，完成后输出三列，最后一次进度为 100
- [ ] 父进程等待全部子进程退出，不留下僵尸进程
- [ ] 完成观测 A；用 `taskset` 完成观测 B

### 3.2 C++17 对照（`sched_cpp`）

- [ ] 对外行为与 C 版相同（参数、工作量含义、输出列、进程模型）
- [ ] 只在 `sched_cpp/` 实现；C++17，不使用异常，不使用 C++20 及更新标准
- [ ] `fork` 之后，子进程不要依赖父进程栈上对象的析构来收尾
- [ ] 用同一组参数与 C 版对照：调度现象应一致，毫秒级数值不必逐条相同

### 3.3 观测

- [ ] 记录本机逻辑 CPU 个数，以及是否绑定到指定逻辑 CPU
- [ ] 完成 2.5 的 A、B；条件允许则做 C；保存 tsv 与图
- [ ] 对照目标写结论：是否看到分时、经过的时间是否被拉长、绑定与不绑定差在哪里

## 4. 后续可扩展点

基础实验完成后再做，不要提前并进第 3 节。每一项仍用「经过的时间–进程」「经过的时间–进度」来解释。

| 方向 | 可以观察什么 |
| --- | --- |
| 工作量计量 | 循环标定与「按进程 CPU 时间忙等」两种做法可切换。比较 `nproc=1` 时经过的时间是否仍接近 `total`，以及系统繁忙时标定是否偏差 |
| 进程数与逻辑 CPU 数 | `nproc` 取 1、逻辑 CPU 数、逻辑 CPU 数 + 1、远大于逻辑 CPU 数，看经过的时间是否大致按 `ceil(nproc / 逻辑CPU数)` 拉长 |
| nice / 优先级 | 一部分进程降低 nice，看进度是否还对称。仍绑定到 1 颗逻辑 CPU，避免与多处理器并行混在一起 |
| 实时调度策略 | 对比 CFS 与 `SCHED_FIFO` / `SCHED_RR`（需要权限）。实时进程是否会让普通忙等几乎不再前进 |
| CPU 亲和性 | 不依赖外部 `taskset`，进程调用 `sched_setaffinity`：绑同一颗逻辑 CPU 对比绑不同逻辑 CPU |
| 控制组 | 设置 `cpu.max` 或 cpuset 后，进度和经过的时间如何变化 |
| 时间片粗估 | 从观测 B 的 tsv 中测量同一 `id` 连续采样的间隔，以及相邻 `id` 切换的间隔，只作粗估 |
| 输出与作图 | 固定 tsv 文件名并一键作图；若子进程各自打印，作图前可按 `elapsed_ms` 排序 |
| C / C++ | 同一组观测条件跑两套程序，确认结论不依赖语言 |

扩展时仍保持：忙等不休眠；`total` / `resol` 含义不变；输出仍是三列。若需要 nice、调度策略、亲和性等，再增加可选参数；默认行为等于本基础实验。
