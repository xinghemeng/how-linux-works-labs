# simple-sched-lab 实验设计

本文说明基础实验要解决什么问题、为什么这样设计、怎样运行和怎样解释结果。代码风格见 `code_review_c.md`、`code_review_cpp.md`。

C 是基准实现；C++17 与之对外行为一致，用来对照学习系统编程。实现不必复刻书中示例源码，但实验目标和要采集、要观察的内容与书中这一节相同。

实现架构、失败处理、任务依赖、完整任务清单和验收矩阵见 [`detailed_design.md`](detailed_design.md)。本文保留实验者需要阅读的目标、程序契约、运行步骤和结果解释。

## 摘要

### 要做什么

实现两个行为一致的命令行程序 `sched_c` 和 `sched_cpp`。程序创建一个或多个持续占用 CPU 的子进程，让每个子进程完成相同数量的 CPU 工作，并记录它们在现实时间中的进度。程序最终输出可以作图的 TSV 数据。

这个 lab 的核心产物不是一个“调度器”，而是一个**调度现象采集程序**：

```text
输入：进程数、每个进程的 CPU 工作量、采样粒度
处理：创建进程 -> 同时开始 -> 忙等消耗 CPU -> 记录进度
输出：每个进程在各个经过时间点达到的进度
用途：比较单进程、单核争用和允许多核并行时的差异
```

### 为什么这样做

教材说多个可运行进程会共享处理器，但只看程序最终完成无法判断进程如何取得 CPU。实验因此固定每个进程的 CPU 工作量，再观察完成这些工作实际经历了多久：

- 只有一个进程时，建立本机基线。
- 两个进程被限制在同一颗逻辑 CPU 时，观察等待调度如何拉长经过时间。
- 两个进程允许使用多颗逻辑 CPU 时，观察并行能力如何缩短完成时间。

三组数据放在一起，才能把“工作量没有变化”和“等待 CPU 的时间发生变化”区分开。

### 怎样完成

1. 先实现 C 基准程序，再实现行为一致的 C++17 对照程序。
2. 用进程 CPU 时钟定义固定工作量，用单调时钟记录现实经过时间。
3. 通过共同开始屏障减少顺序 `fork` 带来的启动偏差。
4. 运行 A、B、C 三组对照实验，保存 TSV 并画采样图和进度图。
5. 根据数据说明争用、分时和可能的并行，不把采样点误写成上下文切换。

### 怎样算完成

- 两套程序具有相同的参数、进程模型和 TSV 格式。
- 每个进程产生预期数量的记录并最终到达 100%。
- A、B 已完成；环境允许时完成 C。
- 保存运行环境、命令、原始数据、两张图和结论。
- 参数错误和运行失败不会留下子进程、僵尸进程或看似成功的半份数据。

建议按“先看结论 -> 第 1 节设计思路 -> 第 2 节程序契约、实验和结果分析”的顺序阅读。第 3 节只是任务概览，第 4 节是基础实验完成后的可选扩展。

## 0. 先理解两种时间

本实验只区分两种时间，全文都用这两套说法，不要混用。

| 说法 | 含义 |
| --- | --- |
| **CPU 时间** | 进程实际占用处理器执行了多久。被调度出去的那段时间不计入。 |
| **经过的时间** | 从某个起点到现在，现实中过了多久。用单调时钟 `CLOCK_MONOTONIC` 测量（不受系统调时影响）。进程在等待 CPU 时，这项仍在增加。输出字段名是 `elapsed_ms`。 |

`total`、`resol` 描述的是要完成的 **CPU 工作量**；`elapsed_ms` 是 **经过的时间**。多个进程争用同一颗逻辑 CPU 时，工作量不变，经过的时间会被拉长。

例如，一个进程先运行 10 ms，等待 CPU 20 ms，再运行 10 ms：它获得了 20 ms CPU 时间，但现实中经过了 40 ms。这个差值就是本实验要观察的对象。

其它固定说法：

| 说法 | 含义 |
| --- | --- |
| **忙等** | 不调用 `sleep`，持续占用 CPU 空转。 |
| **逻辑 CPU** | 操作系统眼里的一颗可调度处理器（超线程也算一颗）。 |
| **参数 `nproc`** | 同时运行的进程个数。与同名命令 `nproc(1)`（查看逻辑 CPU 个数）不是一回事。 |
| **僵尸进程** | 子进程已退出，但父进程尚未 `wait`，进程表项还在。 |

## 1. 实验目标

同时运行一个或多个只做忙等的进程，采集：

1. 每个进程在什么经过时间完成了一段 CPU 工作
2. 每个进程的运行进度

据此核对教材对调度器的描述：可运行进程被分时放到逻辑 CPU 上，可以被抢占；进度随 CPU 时间增加，等待 CPU 时进度不增加。

程序只负责输出数据。不要在代码里断言调度必须均匀轮转。结论写在观测记录里。

实验要回答的核心问题是：一个进程需要完成固定数量的 CPU 工作时，进程数量和可用逻辑 CPU 数会怎样改变它完成工作所经历的现实时间？单进程提供基线；多个进程绑定到同一逻辑 CPU 用来观察争用；允许使用多颗逻辑 CPU 用来观察可能的并行。

采样记录展示 CPU 份额分配后形成的进度，不是内核上下文切换事件。它可以支持“等待 CPU 会拉长经过时间”等结论，不能单独给出准确的切换时刻、时间片长度或进程实际运行的 CPU。

### 1.1 实验问题与变量

| 问题 | 实验前假设 |
| --- | --- |
| 单个 CPU 密集型进程完成固定工作需要多少经过时间？ | 与 `total` 同数量级，通常略大。 |
| 两个进程争用同一颗逻辑 CPU 后会发生什么？ | 两者都能推进；全部完成时间通常接近单进程基线的两倍。 |
| 允许两个进程使用多颗逻辑 CPU 后会发生什么？ | 若实际获得并行资源，完成时间应明显短于单核争用。 |
| 两个进程是否严格交替、进度是否完全相同？ | 不要求；调度器和运行环境可能造成短期不对称。 |

实验主动改变 `nproc` 和允许使用的逻辑 CPU 集合；保持 `total`、`resol`、程序版本和构建配置一致；观测每个进程的 `elapsed_ms`、进度曲线和全部完成时间。同时记录 CPU 集合、容器配额、虚拟化和后台负载，避免把环境变化误当成调度规律。

### 1.2 设计思路是怎样推导出来的

| 要解决的问题 | 设计选择 | 原因 |
| --- | --- | --- |
| 怎样让任务持续参与 CPU 调度？ | 使用忙等进程，不调用 `sleep`。 | 睡眠进程会主动放弃 CPU，无法持续制造竞争。 |
| 怎样保证各进程完成相同工作？ | 用 `CLOCK_PROCESS_CPUTIME_ID` 定义 `total` 和 `resol`。 | 进程等待 CPU 时该时钟不增加，工作量不受等待时间影响。 |
| 怎样看到等待调度带来的影响？ | 同时记录 `CLOCK_MONOTONIC`。 | 单调时钟在运行和等待期间都会增加，可以表示现实经过时间。 |
| 为什么用进程而不是线程？ | 用 `fork` 创建独立子进程。 | 实验主题是进程调度，每个进程也有独立、直观的进程 CPU 时钟。 |
| 怎样减少先创建的进程提前工作？ | 所有子进程先进入共同开始屏障。 | 避免把顺序 `fork` 的启动偏差混进调度结果。 |
| 为什么忙等时不直接打印？ | 子进程写共享记录区，父进程最后统一输出。 | I/O 会干扰计时，并发输出还可能交错或留下半份结果。 |
| 怎样区分争用和并行？ | 比较 A、B、C 三组实验。 | 单独一次运行没有对照，无法判断完成时间变化来自哪里。 |

整个推导可以概括为：

```text
想观察调度
  -> 创建多个始终可运行的进程
  -> 给每个进程相同的 CPU 工作量
  -> 同时记录完成工作所需的经过时间
  -> 用共同起点消除明显的启动偏差
  -> 比较单进程、单核争用和允许多核并行
  -> 用进度曲线解释调度结果
```

## 2. 程序契约与实验方法

### 2.1 命令行

```text
./sched_c   nproc total resol
./sched_cpp nproc total resol
```

| 参数 | 含义 |
| --- | --- |
| `nproc` | 同时运行的进程个数，整数，`≥ 1` |
| `total` | 每个进程要完成的工作量，单位毫秒。含义是「独占 CPU 时大约要跑这么久」，不是 `sleep(total)` |
| `resol` | 采样间隔，单位毫秒。每做完约 `resol` 毫秒的工作记一条。`total` 必须能被 `resol` 整除 |

`nrecord = total / resol`，每个进程恰好 `nrecord` 条记录。参数不合法则向标准错误输出说明原因，并以非零状态退出。

还要校验 `total > 0`、`resol > 0`、`resol <= total`，并执行 `detailed_design.md` 定义的进程数、记录数和共享内存上限。参数错误时标准输出必须为空。

### 2.2 运行过程

1. 父进程在 `fork` 前建立共享记录区和开始屏障。基础实现用 `CLOCK_PROCESS_CPUTIME_ID` 计量工作量，不需要循环标定；若改用书中的循环标定法，必须在 `fork` 前完成标定。
2. `fork` 出 `nproc` 个子进程，实验编号为 `0 … nproc-1`。不要用线程代替进程。
3. 所有子进程就绪后，父进程用 `CLOCK_MONOTONIC` 记下共同起点并释放开始屏障。
4. 每个子进程重复 `nrecord` 次：累计完成约 `resol` 毫秒 CPU 工作，再读一次单调时钟。忙等过程中禁止 `sleep` / `nanosleep`。
5. 进度为 `(i + 1) * 100 / nrecord`（`i` 从 0 计），最后一次为 100%。
6. 子进程只写自己的共享记录区并用 `_exit` 结束。父进程回收全部子进程，确认全部成功后校验、排序并输出记录。失败时必须结束和回收已创建的全部子进程，不留下僵尸进程。

### 2.3 输出

制表符分隔。第一行是表头，随后一行一条记录：

```text
id\telapsed_ms\tprogress
0\t50.127384\t5
```

| 列 | 含义 |
| --- | --- |
| `id` | `0 … nproc-1` |
| `elapsed_ms` | 从共同起点到该采样点的经过时间，毫秒，保留六位小数 |
| `progress` | 该进程进度，百分数 |

分析时横轴用 `elapsed_ms`：某条记录出现，说明该 `id` 当时刚累计完成一份 CPU 工作。记录之间可能经历多次抢占，不能据此还原准确的调度切换。多个进程共享一颗逻辑 CPU 时，各 `id` 的时间戳通常会交错，全部完成的经过时间通常增加；独占一颗逻辑 CPU、或实际获得足够并行资源时，经过时间可能接近 `total`。

### 2.4 实现不必与书中示例相同

书中要点：**用固定工作量的忙等表示「resol 毫秒的工作」，用经过的时间做横轴**。下面可以替换，只要 2.1–2.3 的含义不变。

| 书中做法 | 本仓库可以 |
| --- | --- |
| 空循环标定 `loops_per_msec()` | 用进程 CPU 时钟等到 `resol` 毫秒；若仍用标定，循环不能被编译器删掉 |
| 子进程把时间戳写入缓冲区，结束时自己 `printf` | 子进程写共享记录区，父进程确认全部成功后统一排序和打印 |
| `atoi` / `err` / `warn` | 按本仓库 C / C++ 规范解析参数、处理错误 |
| `fork` 失败时 `kill(SIGINT)` | 能结束子进程并 `waitpid` 即可 |

空语句循环 `for (i = 0; i < n; i++) ;` 在开启优化时可能被删掉。无论是否标定，忙等必须真正占用 CPU。

### 2.5 推荐观测

先查看本机逻辑 CPU 个数（命令 `nproc(1)` 或读 `/proc/cpuinfo`），并用 `taskset -pc $$` 记录当前进程实际允许使用的 CPU 集合。初次试跑可用较小的 `total`；要看清进度趋势，再把 `total` 加大（书中常用秒级，`resol` 为几十到一百毫秒）。

| 编号 | 做法 | 预期（以实测为准） |
| --- | --- | --- |
| A | `nproc=1` | 经过的时间约等于 `total`；只有一个 `id`；进度匀速到 100% |
| B | `nproc=2`，绑定到 1 颗允许使用的逻辑 CPU | 两个 `id` 都能推进但不要求严格交替；经过时间通常接近 A 的两倍 |
| C | `nproc=2`，允许使用至少 2 颗逻辑 CPU | 若实际获得并行资源，经过时间应明显短于 B，并可能接近 A |

把标准输出存成 tsv，画两张图：

1. 横轴 `elapsed_ms`，纵轴 `id`：哪个进程在什么时候留下了采样。
2. 横轴 `elapsed_ms`，纵轴 `progress`，按 `id` 分线：进度如何随经过的时间增长。

每组建议运行至少 3 次，并记录内核版本、CPU 集合、容器或虚拟机环境和明显的后台负载。C 组“不绑定”只表示允许并行，不能证明两个进程实际运行在不同 CPU；需要确认时使用 `perf sched`、ftrace 或扩展记录 `sched_getcpu()`。

### 2.6 工程约定

- 代码只放在 `sched_c/` 或 `sched_cpp/` 内，不要跨目录互相 `#include`。
- 配置与编译：`cmake --preset sched-c` / `sched-cpp`，再 `cmake --build --preset sched-c` / `sched-cpp`。clangd 分别使用 `out/build/sched-c` 与 `out/build/sched-cpp` 中的 `compile_commands.json`。
- 编译选项：`-Wall -Wextra`。不要使用 `-Werror`。

当前 `CMakePresets.json` 的 schema 版本 8 与项目说明中的最低 CMake 版本 3.16 不一致；统一二者是详细任务 C-01 的一部分。如果 CMake 报告 `Unrecognized "version" field`，应先解决 preset 兼容性，不要把它误判为实验代码错误。

### 2.7 结果分析与交付

记录结果时至少填写：

| 项目 | A：单进程 | B：共享一颗 CPU | C：允许并行 |
| --- | ---: | ---: | ---: |
| 运行命令 |  |  |  |
| 允许 CPU 集合 |  |  |  |
| 最大 `elapsed_ms` |  |  |  |
| 相对 A 的倍数 | 1.00 |  |  |
| 是否所有进程到达 100% |  |  |  |
| 异常负载或环境说明 |  |  |  |

结论至少回答：

1. B 相对 A 慢了多少，是否与总 CPU 工作量增加的解释一致？
2. B 中两个进程是否都取得进展，是否存在短期不对称？
3. C 相对 B 是否变快，当前环境是否真的提供了多核执行条件？
4. 哪些是数据直接支持的事实，哪些仍需要调度跟踪工具验证？

基础实验应保留原始 TSV、环境信息、完整命令、两张图和结论文档。建议目录：

```text
results/<date-or-machine>/
├── environment.txt
├── commands.txt
├── single.tsv
├── shared-cpu.tsv
├── parallel.tsv              # 环境允许时
├── samples.png
├── progress.png
└── conclusion.md
```

结论必须写明运行条件、关键数值、观察到的趋势、没有满足预期的地方及可能原因，不能把一次实测写成调度器的固定保证。

## 3. 任务清单

本阶段只做基础实验（与书中这一节同等的内容）。

下面保留里程碑级概览，便于实验者快速了解范围。可执行的任务编号、依赖、失败路径、验证用例和完成条件统一维护在 `detailed_design.md` 第 10 至 12 节；实现时以那份清单为准。

### 3.1 C 基准（`sched_c`）

- [ ] 校验 `nproc` / `total` / `resol`（含 `total` 能被 `resol` 整除），失败则说明原因并以非零状态退出
- [ ] `fork` 前准备共享记录区和开始屏障；所有子进程使用共同起点
- [ ] `fork` 出 `nproc` 个子进程；失败则结束已创建的子进程并 `wait`
- [ ] 子进程做 `nrecord` 次忙等并写共享记录区；父进程校验、排序并输出三列
- [ ] 父进程等待全部子进程退出，不留下僵尸进程
- [ ] 完成观测 A；用 `taskset` 完成观测 B

### 3.2 C++17 对照（`sched_cpp`）

- [ ] 对外行为与 C 版相同（参数、工作量含义、输出列、进程模型）
- [ ] 只在 `sched_cpp/` 实现；C++17，不使用异常，不使用 C++20 及更新标准
- [ ] `fork` 之后，子进程不要依赖父进程栈上对象的析构来收尾
- [ ] 用同一组参数与 C 版对照：调度现象应一致，毫秒级数值不必逐条相同

### 3.3 观测

- [ ] 记录本机逻辑 CPU 个数，以及是否绑定到指定逻辑 CPU
- [ ] 完成 2.5 的 A、B；条件允许则做 C；保存 tsv 与图
- [ ] 对照目标写结论：是否看到分时、经过的时间是否被拉长、绑定与不绑定差在哪里

## 4. 后续可扩展点

基础实验完成后再做，不要提前并进第 3 节。每一项仍用「经过的时间–进程」「经过的时间–进度」来解释。

| 方向 | 可以观察什么 |
| --- | --- |
| 工作量计量 | 循环标定与「按进程 CPU 时间忙等」两种做法可切换。比较 `nproc=1` 时经过的时间是否仍接近 `total`，以及系统繁忙时标定是否偏差 |
| 进程数与逻辑 CPU 数 | `nproc` 取 1、逻辑 CPU 数、逻辑 CPU 数 + 1、远大于逻辑 CPU 数，看经过的时间是否大致按 `ceil(nproc / 逻辑CPU数)` 拉长 |
| nice / 优先级 | 一部分进程降低 nice，看进度是否还对称。仍绑定到 1 颗逻辑 CPU，避免与多处理器并行混在一起 |
| 实时调度策略 | 对比 CFS 与 `SCHED_FIFO` / `SCHED_RR`（需要权限）。实时进程是否会让普通忙等几乎不再前进 |
| CPU 亲和性 | 不依赖外部 `taskset`，进程调用 `sched_setaffinity`：绑同一颗逻辑 CPU 对比绑不同逻辑 CPU |
| 控制组 | 设置 `cpu.max` 或 cpuset 后，进度和经过的时间如何变化 |
| 时间片粗估 | 从观测 B 的 tsv 中测量同一 `id` 连续采样的间隔，以及相邻 `id` 切换的间隔，只作粗估 |
| 输出与作图 | 固定 tsv 文件名并一键作图；若子进程各自打印，作图前可按 `elapsed_ms` 排序 |
| C / C++ | 同一组观测条件跑两套程序，确认结论不依赖语言 |
